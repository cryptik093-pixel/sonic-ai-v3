# 1. PURPOSE
Sonic AI V3 exists to become an **AI-native Producer Operating System**.

Sonic is not merely a chatbot, music analyzer, beat generator, or collection of audio utilities.

Sonic is being built as a persistent intelligence layer that understands:

- the producer
- the project
- the audio
- the production process
- the producer's preferences
- the producer's decisions
- music-production knowledge
- engineering principles
- creative intent
- workflow state
- outcomes over time
The long-term objective is a persistent virtual studio partner capable of assisting with:

- music production
- recording
- audio engineering
- mixing
- mastering
- arrangement
- sound design
- creative development
- education
- project organization
- intellectual-property development
- repeatable production workflows

# 5. AUDIO IS EVIDENCE
Sonic must treat audio as a source of structured evidence.

Where possible, audio claims should originate from actual analysis rather than unsupported language-model speculation.

The preferred architecture is:

```
AUDIO
 ↓
DSP / ML ANALYSIS
 ↓
STRUCTURED AUDIO FACTS
 ↓
AI REASONING
 ↓
RECOMMENDATION
```
Examples of structured audio information may include:

- BPM
- key
- loudness
- peak levels
- RMS
- frequency characteristics
- dynamics
- stereo characteristics
- transient information
- spectral relationships
- detected sections
- detected instruments
- other validated audio features
The LLM should reason over evidence rather than fabricate evidence.

---

# 6. KNOWLEDGE, MEMORY, AND WISDOM
Sonic must distinguish three major forms of intelligence.

## 6.1 Knowledge
Knowledge represents information about music, audio, engineering, production, and related disciplines.

Examples:

- EQ
- compression
- limiting
- dynamics
- acoustics
- harmony
- arrangement
- synthesis
- recording
- mixing
- mastering
- MIDI
- sound design
Knowledge answers:

> **What is known?**

---

## 6.2 Memory
Memory represents what has happened.

Examples:

- producer preferences
- previous conversations
- project history
- previous decisions
- accepted recommendations
- rejected recommendations
- modified recommendations
- previous analysis
- workflow history
Memory answers:

> **What has happened before?**

---

## 6.3 Wisdom
Wisdom represents contextual judgment.

Wisdom combines:

- evidence
- knowledge
- memory
- producer intent
- project context
- goals
- previous outcomes
Wisdom answers:

> **What should we do here, given what we know?**
Knowledge, memory, and wisdom must not be collapsed into a generic undifferentiated memory system.

# 7. PRODUCER-FIRST INTELLIGENCE
The producer is a persistent entity within Sonic.

Sonic should progressively understand:

- creative preferences
- technical preferences
- workflow patterns
- production habits
- engineering tendencies
- artistic goals
- accepted recommendations
- rejected recommendations
- successful workflows
- unsuccessful workflows
The system should learn from actual behavior rather than requiring the producer to manually describe everything.

# 8. PRODUCER DNA
Sonic should eventually derive a dynamic Producer DNA profile.

Potential dimensions include:

```
TEMPO
TONAL PREFERENCES
HARMONIC PREFERENCES
DRUM PREFERENCES
MELODY PREFERENCES
ARRANGEMENT

MASTERING

Producer DNA must remain dynamic.

---

# 9. PROJECT-AWARE INTELLIGENCE
Sonic must understand that a producer's preferences do not always override project intent.

For example:

```
PRODUCER PREFERENCE
        +
PROJECT INTENT
        +
AUDIO EVIDENCE
        +
KNOWLEDGE
        ↓
CONTEXTUAL RECOMMENDATION
```
A producer may generally prefer aggressive low end while intentionally creating a softer project.
Sonic must reason about the current project rather than blindly applying historical preferences.

---

# 10. DECISIONS ARE FIRST-CLASS DATA
Important production and engineering decisions should eventually exist independently of conversational text.

A decision may contain:

```
Observation
Evidence
Interpretation
Recommendation
Selected Option
Reason
Action
Outcome
Producer Response
Timestamp
```
This allows Sonic to understand not only:

> what was said
but:

> what was actually decided and what happened afterward.

---

# 11. FACTS MUST BE SEPARATED FROM JUDGMENT
Sonic should distinguish:

### FACT
Measured or explicitly known information.

### ANALYSIS
A conclusion derived from available evidence.

### INTERPRETATION
AI reasoning about the meaning of that evidence.

### RECOMMENDATION
A proposed course of action.

### PREFERENCE
A producer-specific learned behavior.

### DECISION
The action actually selected.

This separation is essential for reliability and trust.

---

# 12. EVIDENCE AND CONFIDENCE
Where appropriate, Sonic should eventually associate reasoning with:

```
Evidence
Confidence
Source
Timestamp
Scope
```
Sonic should communicate uncertainty honestly.

A measured fact and an engineering hypothesis should never be presented as though they have the same certainty.

---

# 13. PRODUCER AGENCY
Sonic is designed to enhance the producer, not replace the producer's creative authority.

The long-term autonomy model is:

```
LEVEL 0 — EXPLAIN
LEVEL 1 — RECOMMEND
LEVEL 2 — PREPARE
LEVEL 3 — EXECUTE WITH APPROVAL
LEVEL 4 — EXECUTE AUTOMATICALLY
LEVEL 5 — AUTONOMOUS STUDIO ASSISTANT
```
Advanced autonomy must only be introduced after the underlying action, safety, verification, and rollback systems are reliable.

---

# 14. ACTIONS MUST BE VERIFIABLE
Sonic should eventually follow:

```
RECOMMEND
 ↓
ACTION
 ↓
RE-ANALYZE
 ↓
COMPARE
 ↓
VERIFY
 ↓
RECORD RESULT
```
The system should not simply assume that an action succeeded because a tool executed.

The resulting state should be measurable where possible.

---

# 15. LEARNING FROM OUTCOMES
Sonic should progressively learn from:

```
ACCEPTED
REJECTED
MODIFIED
IGNORED
SUCCESSFUL
UNSUCCESSFUL
```
The first objective is not advanced machine learning.

The first objective is reliable structured capture of learning signals.

This creates the foundation for increasingly personalized intelligence.

# 21. ARCHITECTURAL DISCIPLINE
Sonic must be built incrementally.

The preferred development cycle is:

```
DISCOVER
 ↓
PLAN
 ↓
IMPLEMENT
 ↓
TEST
 ↓
REVIEW
 ↓
DOCUMENT
 ↓
VERIFY
```
Do not rewrite working systems merely because a newer idea exists.

Existing working architecture is the baseline.

New architecture should extend and improve the existing system unless evidence demonstrates that replacement is necessary.

---

# 22. SMALL AND WIDE
Sonic should prioritize features that are:

- small enough to implement safely
- broad enough to connect multiple systems
- reusable
- measurable
- extensible
Examples:

- Session Snapshot
- Decision Record
- Memory Context
- Producer Preference Signal
- Before/After Audio Analysis
- Structured Recommendation
A small feature that strengthens five systems is more valuable than a large feature that strengthens one isolated surface.

---

Sonic should prioritize:

```
CORRECTNESS
TYPE SAFETY
MODULARITY
TESTABILITY
OBSERVABILITY
SECURITY
EXTENSIBILITY

Speed matters.

But uncontrolled speed creates technical debt that slows the product later.

The objective is:

> **fast, disciplined progress.**

- a collection of disconnected AI features

- a model-dependent application
- a premature DAW clone
- a feature-chasing experiment
- an architecture rewritten every sprint

# 25. NORTH-STAR STATEMENT
Sonic AI V3 is being built toward:

> **A persistent AI Producer Operating System that understands audio, remembers the producer, understands the project, applies music-production knowledge, reasons about engineering decisions, executes workflows, verifies results, and learns from the producer's creative and technical practice.**
