## Product definition and precedence
The defining purpose of Preset Forge is to generate **fresh, original, prompt-specific, engineered native FL Studio .fst files**, ready for real host load, real sound production and technical/artistic QA. The system is NOT a Patcher-only generator, a design-only JSON producer, a set of renamed/copied states, or a shortcut/manual-guide service. Patcher remains a serious optional advanced processing backend; direct mixer-track FST, individual plugin-state FST, whole mastering and bus chains, insert and recording chains, sends/sidechains and project-aware routing are all first-class requirements. No developer may narrow this scope merely because a narrower workflow is easier.

## Non-negotiable engineering path
`Prompt/Audio → SoundIdentitySpec → PluginCapabilityProfile → Original ChainGraphIR → Physical-unit ParameterPlan → Isolated Host Job → NEW native .fst → DAW reload/readback → Dry/Processed/Reload renders → Matched-volume audition → Provenance/rights → Release manifest`.

**Native output backends:** (A) direct mixer track state; (B) individual effect state; (C) Patcher graph state; (D) mixer state(s) PLUS project routing companion where required; (E) cautiously experimental version-calibrated binary writer after current host proof. Never promise arbitrary mixer-side sends/sidechains are fully restored by a single FST when FL project routing is required.

**Parameter discipline:** current planning axes are `character/control/space/tone` 0–100. Stored Crown Patcher controls are `CHARACTER/PRESSURE/AIR/WIDTH`. They are not interchangeable without measured host readback; current planner derives intentions (drive, ratio, attack/release, wet return, tempo delay, reverb, EQ tilt, tentative threshold), not already calibrated plugin state. Preserve exact plugin names and verify installed versions/licenses, normalized-to-physical transfer functions, bypass/wet, smoothing and safe bounds. Do not invent pitch/formant/autotune processing.

## Runtime and proof gates
Real Windows/FL Studio must save a genuinely new state from a **prompt-specific** graph, not simply rename or change loudness of an old FST. Each candidate needs a unique native SHA-256, graph and parameter manifest, plugin dependency proofs, clean reopen with matching state, same-source rendered audio, real speaker playback and level-matched listening notes. LUFS/true peak only from a verified meter. A green test or structurally parsed FST cannot be marked audio-approved or sale-ready.
